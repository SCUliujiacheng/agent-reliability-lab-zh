# 运行时实现笔记

`timeout-recovery` 是最短的一条检查路径。第一次日志查询被注入超时，resilient 模式记录失败、重试，再保存检查点和最终结果。这个场景用来确认：重试发生在正确的逻辑动作上，失败尝试没有丢失，评分器也能从记录里找回这次恢复。

## 从一次运行开始

```text
uv run arl run scenarios/incident-response/timeout-recovery.yaml --mode resilient --database .arl-data/demo.db --json
```

复制输出中的 `run_id`，导出轨迹：

```text
uv run arl export-trace <run-id> --database .arl-data/demo.db --output artifacts/trace.json
```

预期顺序是注入超时、失败尝试、重试、成功尝试、检查点和最终结果。页面也可以查看同一类记录，见[轨迹截图](screenshots/trace-detail.png)。

`approval-reconstruction` 检查另一条路径：运行停在待审批动作上，服务围绕同一 SQLite 数据库重建，再提交审批。相同决定重复到达时，应只保留一条 `approval.recorded` 事件和一次写操作。

## 策略与工具为什么固定

当前实验先检查编排：同样的动作遇到同样的故障，两种运行模式会留下什么结果。脚本策略和本地工具让这些条件可以重复，也使评分器能够比较确定的输出。

可选 OpenAI 兼容适配器保留了接入模型的入口，但没有进入这组基准。真实模型会改变动作选择和调用顺序，需要记录模型、提示词版本，并重复运行观察波动。用这里的六个场景结果无法推断模型质量。

## SQLite 中保存什么

运行状态、检查点、审批和事件保存在同一个数据库。状态转换与对应事件在一个事务中写入，乐观版本检查防止旧状态覆盖新状态；WAL 支持本地并发访问。这样重建应用对象后仍能读回待处理动作。

执行租约和幂等结果也通过存储层协调。这里测试的是共享一个 SQLite 数据库的应用实例，不包含多节点数据库、队列或数据库迁移。

## 两个审批同时到达

审批必须带上当前动作的 `action_step` 和 SHA-256 指纹。一个事务只会在运行仍等待该动作时记录决定。相同的并发决定归为一次记录；两个决定冲突时，其中一个返回 HTTP 409。

高风险写操作要求幂等键，工具结果在取得执行租约后缓存。测试中的保证是：两个应用实例共享一个 SQLite 数据库时，相同审批留下一个决定和一次模拟写入。这不能推导为任意外部服务的 exactly-once 保证。

`actor` 目前只是请求中的字符串。身份认证、授权和审批有效期尚未实现。

## 调用预算与取消

每次新策略调用前，运行时先持久化预留一个名额；默认最多 64 次，允许配置 1–1024 次。取消后重建运行不会重置额度。返回 `finish` 的调用也占用一次名额，工具重试不额外计数。

审批恢复会继续执行暂停前选定的动作，不再次预留。额度耗尽时，运行时一起写入终态和带有 `action_budget_exhausted` 的 `run.failed`，随后停止策略调用。

次数限制不能约束每次调用的时长。自定义 `Policy` 仍需限制自己的 I/O；可选 HTTP 适配器有 45 秒总时限。

## 报告为什么要重算

JSON 报告可以被改动，汇总数字与轨迹也可能不一致。gate 先检查场景、动作身份、事件顺序、唯一性和确定性输出，再由逐题记录重算指标，最后对照基线。如果这些记录对不上，结果是基础设施错误，而非 `PASS`。

场景哈希和来源字段的规则见[场景与报告说明](data-and-scenario-provenance.md)，指标分母见[实验结果](benchmark-results.md)。

## 接口与数据限制

只有已注册、通过 Pydantic 输入校验的工具可以执行，输出也会再次校验。持久化前递归脱敏，API 返回比内部事件更少的字段。

请求体有大小限制，CORS 来源显式配置，API 校验 Host，Nginx 拒绝未知虚拟主机。Compose 提供的浏览器响应禁止嵌入框架。应用路由返回稳定的 JSON 错误；外层 Host 检查可能返回普通 400 或空的 Nginx 444。

可选模型适配器限制远程 HTTPS、重定向、响应编码、总时长和响应字节数，具体配置见[本地开发](local-development.md)。这些检查不提供身份认证或租户隔离；工具副作用也仍是模拟。

## 后续可以单独验证的方向

多工作进程需要数据库租约、服务端时间和恢复队列，还需测试争用与故障时序。迁移到 PostgreSQL 之前，应先补数据库迁移和负载测试。

真实模型评测则保留脚本套件作对照，另建模型套件，记录模型和提示词版本，重复运行并分别报告确定性检查和质量统计。两类实验的问题不同，结果也应分别记录。

组件之间的关系见[架构图](architecture/agent-reliability-lab-architecture.html)。
